# Checks are probes, not executors

A check command is a read-only probe of observable facts (process liveness, file markers, ports, remote state) — it must not perform the work it observes. Side-effecting work (installing dependencies, running builds, pushing images) belongs to the session's own tools; the daemon watches the work's observable effects. Without this boundary the events daemon silently becomes a persistent job runner, and delivery semantics (retry, two-stage ack) would be re-purposed as execution semantics (re-run side effects on retry) they were never designed for. Profile templates are audited against this rule; the ad-hoc `subscribe(check)` path inherits it as a documented contract — validate surfaces a warning on known side-effect patterns rather than blocking. Modeled scenario: "uv pip install" failure becomes `pgrep -f 'uv pip install' || test -f .venv/.stamp`, watching the session's own run.
